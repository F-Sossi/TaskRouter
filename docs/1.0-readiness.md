# What stands between `0.1.0-preview.14` and 1.0

A full review of the library on **2026-10-21**, at `main` `a0a23d1` (`0.1.0-preview.14`, published
2026-10-20). **Section A is cleared:** A1–A3 were fixed in `0.1.0-preview.15`, A4–A9 in
`0.1.0-preview.16`, each with a regression test against SQL Server — A8 included, under
read-committed snapshot. The descriptions below record the behaviour as it was found. A second
review of `preview.15` found more, fixed in the same release; see [section E](#e-second-review-fixed-in-preview16).
What is left before a release candidate is in sections B and C.

Each item says how it was established:

- **Confirmed** — reproduced by a test against SQL Server during the review.
- **From the code** — read and traced, not run.
- **Unverified** — a risk the code allows, not reproduced.

Section A is the list to clear before cutting a release candidate. Sections B and C follow; D is
drift already fixed in this pass.

## A. Defects — fix before 1.0

### A1. An event raised twice on one task fails the second operation — Confirmed

**Fixed in `0.1.0-preview.15`.**

The idempotency key is `definitionId:taskId:event`
(`TriggerDispatcher.IdempotencyKey`), and both `TaskRouterTriggerExecutions` and `TaskRouterOutbox`
have a unique index on it. Any event that can happen more than once to the same task collides on
its second occurrence. The `DbUpdateException` rolls back **the whole operation**, not just the
trigger.

- **Reproduced:** a "Step is assigned" trigger on a step, then reassigning that step twice. The
  second `ReassignTaskAsync` fails with
  `Cannot insert duplicate key row … IX_TaskRouterTriggerExecutions_IdempotencyKey … (8:2:TaskAssigned)`.
- **The same shape:** `SubWorkflowCompleted` / `SubWorkflowCancelled` on a parent with more than
  one sub-workflow, and `Custom` events raised more than once.
- **Why it matters:** "notify the new assignee when a step is reassigned" is the first thing a host
  configures, and with it a step can never be reassigned twice.
- **Fix:** key repeatable events on something unique to the occurrence (the log entry's id, or a
  per-task sequence), keeping the plain key for the events that really are once per task.

### A2. Cancelling the last open branch of a fork ends the run instead of converging — Confirmed

**Fixed in `0.1.0-preview.15`.**

Convergence is only checked when a branch is **completed** (`RouteFromAsync` →
`HandleConvergenceAsync`). Cancelling a branch never reaches it. Once the last open branch is
cancelled, `MaybeCompleteRunAsync` finds no open tasks and marks the run **Completed**. The
convergence step is never created.

- **Reproduced:** fork Provide Input into C100 and C200, complete C100, cancel C200. The run reads
  `Completed` with zero PM Review tasks.
- **Fix:** cancelling a fork task should run the same convergence check as completing one.
  Converging with every branch cancelled also needs a decision: converge or cancel the fork.

### A3. "Complete" on a convergence step with nothing sent back skips completion — Confirmed

**Fixed in `0.1.0-preview.15`.**

`CompleteWithSelectiveRejectionAsync` with an empty rejected list has its own inline completion
(`WorkflowEngine.Fork.cs`, the "straight approval" branch) rather than going through `FinishAsync`.
So it:

- fires no `TaskCompleted` triggers (reproduced: zero executions);
- does not hand the step to whoever completed it (reproduced: the assignee stayed
  `user-originator` after `user-section-lead` completed it — the preview.7 rule);
- does not close the sub-workflow instance if the convergence was its last step, so a blocking
  instance keeps its parent blocked for good *(from the code)*;
- does not requeue a parent that closes itself *(from the code)*.

The runner reaches this path every time somebody picks a rework outcome on a convergence step and
then sends no branch back. The completion preview mirrors the same behaviour, so the confirmation
is consistent with the defect: it lists no step-completed actions.

**Fix:** route the straight approval through `FinishAsync`.

### A4. The reminder sweep can starve — From the code

**Fixed in `0.1.0-preview.16`.**

`ReminderCandidatesAsync` takes `OrderBy(Id).Take(batchSize)` from **every** open task with a
reminder lead time, deliberately without a date filter. A task that is not yet inside its window
stays a candidate, and so does one whose resolver returns null. Once 100 such tasks sit at the low
end of the id range, every pass examines the same 100 and no later task is ever reminded.

The comment's claim that the set "shrinks as each one fires" holds only when everything examined
is due. The overdue half avoided the same trap by filtering on `DueDate`, as its comment explains.

**Fix:** narrow on a generous outer bound, as the comment itself suggests
(`DueDate == null || DueDate <= now + maxLeadTime + slack`). Tasks whose resolver returns null
need either a separate slow pass or a claim with a retry-after stamp.

### A5. Two app instances process the same outbox message — From the code

**Fixed in `0.1.0-preview.16`.**

`OutboxProcessor` claims messages by **reading** the due rows and then setting `LeaseId` and
`LeasedUntil`. There is no conditional update and no concurrency token
(`WorkflowModelBuilder` declares none). Two instances polling together both read the same rows and
both process them, so notifications and webhooks go out twice.

A single instance is safe. A web farm or a second worker is not.

**Fix:** claim with `ExecuteUpdateAsync … WHERE LeaseId IS NULL OR LeasedUntil < now`, the way
`DeadlineProcessor` already does, then load only the rows this instance claimed.

### A6. Automatic sub-workflows and "step created" do not fire on every creation path — From the code

**Fixed in `0.1.0-preview.16`.**

`SpawnAutomaticAsync` says it is "called wherever a task is created". Two paths miss it:

- **A sub-workflow's own entry task** (`SpawnAsync`): automatic attachments on it never start.
- **Branches added to a running fork** (`AddBranchToForkAsync`): no automatic sub-workflows. This
  path also raises only `BranchAdded`, never `TaskCreated`, so "Step is reached" triggers do not
  run for an added branch.

### A7. Discarding a test run — From the code

**Fixed in `0.1.0-preview.16`.**

- **Outbox rows are left behind.** `TestRunTeardown` deletes logs, executions, variables, instances
  and manifests, but not outbox rows, and the outbox has no foreign key to the task. A test run's
  after-commit notification still pending when the run is discarded fails five times
  (`SingleAsync` on a missing task), is abandoned, and logs an error each time.
- **It is not atomic.** Three `SaveChangesAsync` calls with no transaction around them, so a
  failure part-way leaves half a run.

### A8. Simultaneous completion of the last two branches — Unverified

**Fixed in `0.1.0-preview.16`.**

`HandleConvergenceAsync` counts the other open branches, then acts on the count. Its comment
relies on the transaction and on the unique index on `ForkManifestId`. That index stops **two**
convergence steps; it does nothing about **none**.

- **Database with `READ_COMMITTED_SNAPSHOT` on:** each transaction can read the other's branch as
  still open, both log "waiting", and the fork never converges.
- **Locking read committed:** the two deadlock and the execution strategy retries the loser, which
  then finds no open branch and converges. That is correct, but only by luck of configuration.

This is the same family as open item 6 in STATE.md (a run-scoped variable inserted by two branches
at once). Worth a test under RCSI, and an update lock on the manifest row if it reproduces.

### A9. Carried over from STATE.md

**Fixed in `0.1.0-preview.16`.**

- `WorkflowTransaction` retries can reuse a stale change tracker, so a retried attempt may skip a
  change as "unchanged".
- Two forked branches completing at the same moment can both insert the same run-scoped variable.
  The second fails on the unique index.

## B. Smaller behaviour issues

- **`CancelTaskAsync` and `ReassignTaskAsync` accept a forked origin task.** Cancelling it
  overwrites `Forked` with `Cancelled`, which `CancelInstanceAsync` takes pains never to do.
- ~~**Rework does not go back to whoever did the branch.**~~ Fixed in `preview.16`: the manifest
  records who completed each branch, and rework starts with them (a configured assignment role
  still decides first). Rework carries `ParentTaskId`.
- ~~**A convergence step does not inherit `ParentTaskId`.**~~ Fixed in `preview.16`.
- ~~**After-commit triggers see less branch context than in-transaction ones.**~~ Fixed in
  `preview.16`: the outbox message carries the task and branch as they were at the event.
- ~~**Publishing does not check conditions.**~~ Fixed in `preview.16` for the builder: a
  malformed trigger condition or an unregistered route condition is refused at publish. (This
  item said a skipped route "can stall a run". It was worse: with nothing else open the run
  completed. A step with no matching route is now refused instead.)
- **`CancelRunAsync` reports a missing run as a plain `InvalidOperationException`** (HTTP 400)
  where everything else uses `WorkflowNotFoundException` (404). It also raises `RunCancelled` only
  when the run had an open task, and no `TaskCancelled` for the tasks it closes.
- **Notify's "next assignee" depends on matching timestamps.** It finds the next steps as tasks
  whose `Created` equals the completed step's `CompletedDate`. That is correct today because every
  creation path stamps the completion's `now`, but nothing enforces it; a predecessor column would.
- **Nothing is paged:** the inbox, runs for a subject, the actor directory and the builder's people
  fallback all return everything.
- **Nothing is ever deleted:** the outbox, trigger executions and task logs have no retention.
- ~~**Event order differs at convergence.**~~ Fixed in `preview.16`: every creation path raises
  `TaskCreated`, then spawns.
- ~~**Tidying:** the misplaced `_subjectsByRun` summary, and `AutoFocus` on
  `RunnerConfirmActionsDialog`'s button.~~ Fixed in `preview.16`.

## C. Packaging and public API

- **Undocumented public members: 794** — Core 442, EntityFrameworkCore 240, AspNetCore 56,
  Blazor 56. `CS1591` is suppressed in `src/Directory.Build.props`; STATE.md's figure of 708 is
  from the packaging pass.
- **No API baseline.** There is no `Microsoft.CodeAnalysis.PublicApiAnalyzers` and no
  `EnablePackageValidation` with `PackageValidationBaselineVersion`. After 1.0 a breaking change
  would ship unnoticed. Add both at the release candidate and baseline against it.
- **Schema policy.** Entities are public with public setters, and the host owns migrations, so
  every model change is a migration in every host. 1.0 needs a stated rule: which version parts
  may change the schema, and that each such release lists its migration.
- **Supported platforms are unstated.** It targets `net10.0` only. The tests run on SQL Server
  only; the first host also runs its own tests on SQLite.
- **No changelog.** Release notes live in STATE.md among session notes. A `CHANGELOG.md` (and
  release notes on the GitHub release) is what a 1.0 consumer reads.
- **Transaction composition is documented in `docs/design.md` only.** A host wrapping several
  engine calls in its own transaction must run `IWorkflowPostCommitActions` itself, or after-commit
  triggers never fire. Neither the README nor `IWorkflowEngine` says so.
- ~~The test project built with two MSTest analyzer warnings.~~ Fixed in `preview.15`.

## E. Second review, fixed in `preview.16`

An external review of `preview.15` on 2026-10-21 reported 22 issues, 16 of them not already in
this document. 14 were reproduced against SQL Server before fixing, the rest confirmed from the
code. All are fixed in `0.1.0-preview.16`, with regression tests in `ReviewConsistencyTests` and
`NestedTransactionTests`:

- Two concurrent completions of one step both succeeded, each creating a successor.
- A rolled-back operation left the context believing it had happened; the next call was
  refused as "already completed".
- A trigger calling back into the engine dropped a terminal step queued to close itself.
- An ad-hoc step could come from another workflow's definition, or be added under a finished run.
- A default route was followed alongside a matching route, and a default route ignored its own
  condition.
- A step with no matching route completed and ended the run.
- Selective rejection took the first route for the outcome, ignoring the rework flag and
  conditions.
- Queued triggers saw the latest assignee, not the one they were raised for.
- `RaiseEventAsync` stored a variable and raised nothing.
- The completion confirmation missed steps that close themselves, and what follows them.
- Rework vanished from the origin view; progress collapsed parallel branches into one.
- The HTTP runner dropped the reason for cancelling a run.
- Two concurrent publishes could leave two latest versions.
- Run-scoped variables had no uniqueness guard at all; a duplicate broke every later
  completion in the run.

The changes for a host, with the SQL to run before upgrading, are in
[`consistency-upgrade.md`](consistency-upgrade.md).
